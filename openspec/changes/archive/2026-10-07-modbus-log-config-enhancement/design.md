# Design

## Context

记录仪由单个 logger 任务以轮询方式读取三路串口并落盘。实现前存在三类约束：帧缓冲只有 16 字节且间隙阈值固定为 40ms（与波特率无关），导致 Modbus 帧被拆断/合并且无方向标识；串口、WiFi、桥接配置分散于三处 NVS；设备内部 SRAM 同时承载 BSS 与堆，BLE+WiFi+httpd 共存时内部内存余量很小（见 AGENTS.md 初始化顺序与内存约束）。本设计的三个新增模块 `app_modbus`、`app_config` 与 logger/bridge 的改造均须在这些约束下工作。

## Goals / Non-Goals

**Goals:**
- 不依赖精确的每字节硬件时间戳，即可在轮询架构下准确还原帧边界。
- 配置同步对屏幕/Web/控制台所有现有调用点透明，无需逐一改造调用方。
- 全部增强不压缩 BLE/WiFi 可用的内部内存，不改变既定初始化顺序。

**Non-Goals:**
- 不替代 NVS：config.json 是可编辑/可迁移的外部副本，NVS 仍是运行期配置来源。
- 不实现 Modbus 主站逻辑、不主动发起总线事务。
- 不改变日志文件目录组织与分段滚动机制。

## Decisions

### 1. 帧边界：波特率自适应 3.5 字符时间 + ASCII 分隔符
二进制帧间隙按 `11 位 × 3.5 / 波特率` 计算，高波特率（≥19200）按 Modbus 规范固定 1.75ms；ASCII 帧以 `:` 与 CRLF 界定。相比原先固定 40ms，低波特率（如 19200 下 3.5 字符 ≈ 2ms）不会误切，也不会把连续流错误合并。
备选：固定保守间隙（如 50ms）——在轮询架构下无法同时满足「不误切」与「不并帧」，放弃。

### 2. 自适应快速轮询还原跨周期时序
帧横跨多个轮询周期时，FIFO 内字节的驻留时间会被误算成总线静默。采用有数据/有帧组装中时 1ms 轮询、全端口空闲时 8ms 轮询：1ms 窗口内连续流的字节发送时长必然填满窗口、估算静默≈0，而真正 ≥3.5 字符的帧间间隙会在连续空读后被检出。静默估算公式：`窗口长度 − 本批字节数 × 单字节线时长`（下限为 0）。
备选：UART RX 中断逐字节打时间戳——需要新增中断与每字节开销，改动热路径，放弃。

### 3. 大缓冲与 cJSON 全部置于 PSRAM
帧缓冲、8KB 配置读写缓冲、快照缓冲均为 PSRAM 动态分配；通过 cJSON 内存钩子让 cJSON 节点与打印串也在 PSRAM。实测这使 WiFi 启动前内部堆从 76KB 恢复到 112KB（基线 113.7KB），是 httpd 能成功启动的关键。
备选：保留内部 BSS 静态数组——直接挤占内部堆，实测导致 beacon 分配失败、httpd 无法启动，放弃。

### 4. 配置变化检测采用 canonical 快照，自动导出
logger 每 2 秒由三处当前配置构建一行固定格式 JSON 串，与上次快照逐字符比对，不同即导出。屏幕/Web/控制台的修改最终都落到相同的 NVS/内存状态，因此无需修改任何调用点即可实现「来源无关」的自动双向同步。
备选：在每个 save 调用点显式触发导出——需改动多处 UI/网页代码且易遗漏，放弃。

### 5. 出站队列统一所有 TX 路径
TCP/BLE 下发、测试、周期发送、控制台注入统一进入 logger 的出站请求队列，由 logger 在自身上下文执行「结束当前 RX 帧 → 写入 UART → 等待发送完成 → 短窗口排空并丢弃 RX → 记录 TX 帧」。这保证 TX 只记录一次、回环 echo 不被当成总线数据。
备选：各调用方自行写串口并记录——时序与 echo 处理分散，容易重复或漏记，放弃。

### 6. 配置文件原子替换，FatFs 差异处理
写临时文件 → 备份现有 config.json → 删除目标 → rename 临时文件为 config.json。FatFs 的 rename 在目标已存在时会失败（不同于 POSIX），故必须先 remove。

## Risks / Trade-offs

- [被动监听时 fc 05/06 等定长帧的请求/应答形态相同] → 以「addr+fc 待应答」配对状态机消歧；无法判定时只标 `RX`，不臆测角色。
- [1ms 快速轮询提高 CPU 唤醒频率] → 仅在有流量或帧组装期间生效，总线空闲立即回到 8ms；logger 本身处理很轻，实测不影响抓取与其他任务。
- [config.json 写一半或介质异常] → 临时文件 + 替换流程保证旧文件完整，启动与上传严格校验，失败回退 NVS 并保留 .bak。
- [WiFi/透传等部分配置运行期变更不能即时生效] → 导入即持久化，需重启生效的参数在界面明示；串口参数仍按原 reload 机制即时生效。
